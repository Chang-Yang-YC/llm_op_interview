Ring All-Reduce · 两阶段可视化

n = 4 个 rank 排成环，数据切成 n 块（A / B / C / D，块 0~3） · 共 2(n−1) = 6 步 · 每步每卡只发送 data / n · 方向恒为 r → (r+1) % n

Phase 1 Reduce-Scatter（前 n−1 步）

每步把自己负责的一块发给右邻居，同时把左邻居发来的同名块原地累加（add_）。结束时 rank r 恰好持有完全归约的块 r，各管一摊。

Phase 2 All-Gather（后 n−1 步）

把已归约好的 Σ 块沿环转发（不累加、copy_ 直接覆盖）。n−1 步后每个 Σ 块绕环一周，所有卡集齐全部结果。

带宽 必背公式

每卡总发送量 = 2(n−1)/n · data ≈ 2·data，与卡数 n 无关（带宽最优）。busbw = data · 2(n−1)/n / time。

R3 → R0（回到起点，构成环）
块 A(0) 块 B(1) 块 C(2) 块 D(3) Σ = 已完全归约 顶部金条 = 本步发送 底部红条 = 本步接收 灰色淡化 = Phase 2 中已废弃的中间结果

接力棒直觉 —— 索引公式为什么长这样

把块 j 的部分和想象成一支接力棒：从 rank (j+1)%n 起跑，每传一站就累加该站 rank 的本地分量，n−1 步后绕环一圈回到主人 rank j 手里，恰好加满 n 份。以块 A（j=0, n=4）为例：

R1 起跑(A₁) → R2 (+A₂) → R3 (+A₃) → 回到 R0 (+A₀) = ΣA

第 s 步持有并发出块 j 接力棒的正是 rank (j+1+s) % n；把 j 反解出来就是代码里的 send_idx = (r−s−1) % n。发送块与接收块恰好错开一位还有工程原因：isend 的张量在 wait() 完成前不能被改写，所以发送块和接收累加块必须是不同的块。Phase 2 同理，只是接力棒换成了"已经算完的 Σ 块"，从主人自己手里起跑，因此索引整体偏移 1 位（send_idx = (r−s) % n）。

带宽账 —— 为什么 ring 是带宽最优的

方案每卡传输量随 n 增长
Naive：先 all-gather 全量，再本地求和(n−1)·data线性恶化
Ring：reduce-scatter + all-gather2(n−1)/n · data≈ 2·data，恒定
  • 每步每卡只发 data/n，共 2(n−1) 步；n→∞ 时每个字节约"被发 2 次"：一次为了归约，一次为了广播。
  • 任何时刻所有 n 条相邻链路都在同时传数据，没有热卡，链路利用率恒定。
  • 代价是延迟：串行 2(n−1) 步，随 n 线性 → 小消息用 tree，大消息用 ring（NCCL 的选择逻辑）。

对应代码（comm/c01_ring_allreduce.py）

  • Phase 1（ring_allreduce 内 "phase 1: reduce-scatter" 段）：recv_buf 与发送块分开分配；chunks[recv_idx].add_(recv_buf) 原地累加。
  • Phase 2（"phase 2: all-gather" 段）：chunks[recv_idx].copy_(recv_buf) 必须写回张量视图保持 in-place——只重绑定列表元素不会写回原张量（常见 bug）。
  • 索引注释：若误用 (r−step)/(r−step−1)，归约块的归属会错位成块 (r+1)%n，Phase 2 会转发未归约的数据。
  • 坑：逐条 isend/irecv 会懒创建 2-rank 通信子，ring 首发顺序构成循环依赖 → 死锁；正确姿势是 dist.batch_isend_irecv + P2POp。
